# Трекер домашних задач — ПР11

Текущая версия добавляет формы Django для фильтрации, создания и редактирования
задач, отмену, подтверждение удаления и загрузку изображений.

## Запуск

```bash
source .venv/bin/activate
uv pip install --python .venv/bin/python -r requirements.txt
python manage.py migrate
# Только для новой базы:
python manage.py import_legacy
python manage.py runserver
```

Вместо uv можно использовать `python -m pip install -r requirements.txt`, если
pip установлен в окружении. Страница задач: http://127.0.0.1:8000/tasks/.
Ссылка «Добавить задачу» открывает форму. В карточке доступны редактирование,
отмена активной задачи и удаление с подтверждением. Админка ПР10 сохранена.

## Формы и маршруты

| Форма / действие | Маршрут | Обработка |
|---|---|---|
| `TaskFilterForm(forms.Form)` | `/tasks/` | GET: категория, статус, поиск, диапазон сроков, сортировка |
| `DueDateForm(forms.Form)` | `/tasks/due/` | GET: активные задачи к дате |
| `TaskForm(ModelForm)` | `/tasks/create/` | GET: пустая форма; POST: проверка и создание |
| Та же форма с `instance` | `/tasks/<id>/edit/` | GET: текущие данные; POST: изменение той же записи |
| Отмена | `/tasks/<id>/cancel/` | Только POST; ACTIVE → CANCELLED |
| Удаление | `/tasks/<id>/delete/` | GET: подтверждение; POST: удаление |

Формы описаны в `task_pages/forms.py`; представления используют `is_valid()`
и `cleaned_data`. Поля оформлены Bootstrap, ошибки и подсказки выведены общим
шаблоном `includes/form_fields.html`. После успешного POST происходит redirect;
обновление страницы результата не повторяет запись. Пустой POST остаётся
связанной формой с ошибками. Несуществующие объекты возвращают 404.

## Валидация и правила трекера

- Название после удаления пробелов по краям — от 3 до 200 символов.
- Категория должна существовать, статус выбирается из `Task.Status`.
- Новый или изменённый срок не может быть раньше сегодняшнего дня.
  При редактировании старой просроченной задачи исходный срок можно сохранить,
  например чтобы отметить её выполнение. Фильтр разрешает исторические даты.
- `TaskForm.clean()` отклоняет активный дубликат с тем же названием, категорией
  и сроком. Проверяемая запись исключается через `exclude(pk=instance.pk)`;
  выполненные и отменённые записи не блокируют создание активной задачи.
  Разные задачи одной категории на одну дату допустимы.
- `TaskFilterForm.clean()` проверяет порядок границ периода. Неверные параметры
  (в том числе сортировка) дают ошибки и пустой список; фильтры и пагинация
  сохраняют параметры. Это заменяет прежнее молчаливое исправление сортировки.
- Описание — необязательное многострочное поле, до 2000 символов в форме.
- Все изменяющие POST-формы содержат CSRF-токен. GET не создаёт, не отменяет
  и не удаляет задачи. Отмена выполненной задачи не меняет её статус.

Проверка дубликатов и дат реализована в пользовательской форме; это не
ограничение уникальности базы и не гарантия от одновременных запросов.
Админка и прямые ORM-записи не используют эти дополнительные правила формы.
Как и предыдущие публичные страницы учебного трекера, новые формы не имеют
проверки владельца или входа; права пользователей не входят в эту практику.

## Изображения и миграция

Миграция `0003_task_description_task_image` добавляет `description` и `image`.
Существующие записи сохранены, новые поля необязательны. Резервная копия:
`data/django_backup_pr11.sqlite` (локально, исключена из Git).

`ImageField` хранит путь, файлы лежат в `media/tasks/<год>/<месяц>/`.
Настроены `MEDIA_ROOT` и `MEDIA_URL`; Django раздаёт медиа только в DEBUG.
Форма использует `multipart/form-data` и `request.FILES`, Pillow проверяет
содержимое. Принимаются PNG/JPEG/WebP до 5 МБ. Без изображения карточка
показывает соответствующий текст. При ошибке формы файл нужно выбрать повторно.
При редактировании без новой загрузки изображение сохраняется; флажок очистки
удаляет ссылку из модели. По стандартному поведению Django прежние файлы при
замене/очистке/удалении записи не удаляются из хранилища автоматически.
Медиафайлы и локальная база исключены из Git.

## Что изменилось в ПР10

- Админка на русском: названия, столбцы, поиск по задаче и категории,
  фильтры по статусу, категории, дате и году, сортировка, по 20 строк на странице.
  `TaskInline` позволяет редактировать задачи в карточке категории.
  Число задач категории вычисляется `Count`; список задач использует JOIN.
- `Task.Status(TextChoices)`: `active`, `completed`, `cancelled`.
  `is_completed` остался только свойством для чтения в старых шаблонах.
  Для изменения/фильтрации использовать `status`, например
  `task.status = Task.Status.COMPLETED; task.save(update_fields=["status"])`.
- Миграция `0002_task_status_slug_year` сначала добавляет поля, переносит
  `False → active`, `True → completed`, назначает `task-<id>` для старых задач,
  затем вводит уникальность slug и удаляет старое поле. Откат преобразует
  отменённые в невыполненные: булево поле не представляет третий статус.
- QuerySet: `active()`, `completed()`, `cancelled()`, `overdue()`, `due_by(day)`,
  `with_category()`. Методы объединяются в цепочки и применены в представлениях.
  Отменённые задачи не попадают в активные, просроченные и поиск задач к дате.
- `deadline_year` — сохраняемое `GeneratedField(ExtractYear("deadline"))`;
  SQLite вычисляет год при записи. Поле используется фильтром админки.
- `/tasks/by-slug/<slug>/` открывает карточку; `get_absolute_url()` возвращает
  этот адрес. Старый `/tasks/<id>/` продолжает работать. Для новых задач slug
  состоит из ASCII-названия (или `task`) и UUID, при переименовании сохраняется.
- Статистика показывает все три статуса. Контекстный процессор передаёт название
  сайта и ленивый счётчик активных задач в общую навигацию.

# Трекер домашних задач — ПР9

Текущая веб-версия использует Django ORM и SQLite `db.sqlite3`.

## Запуск текущей версии

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py import_legacy
python manage.py runserver
```

Открыть http://127.0.0.1:8000/. Исходная база ПР7 — `data/tracker.sqlite`.

Весь импорт атомарен: ошибка откатывает внесённые этим запуском записи.

для обычного запуска сайта повторять его не нужно.

Перед переходом сохранены локальные копии `data/tracker_backup_pr9.sqlite`
и `data/django_backup_pr9.sqlite` (исключены из Git). Исходная база не менялась.
`db.sqlite3` уже отслеживалась в репозитории и оставлена как демонстрационная
база; её можно восстановить с нуля командами миграции и импорта выше.

## Модели и структура

В `task_pages/models.py` находятся:

- `Category`: автоматический ID, уникальное название `CharField(200)`.
- `Task`: автоматический ID, название `CharField(200)`, `DateField` срока,
  `BooleanField` выполнения (по умолчанию `False`), `ForeignKey` категории.
- Связь `Category → Task` — один ко многим; обратная связь `category.tasks`.
  `PROTECT` запрещает удалять категорию с задачами.
- `Task.is_overdue` вычисляет просрочку: задача не выполнена и срок меньше
  текущей даты в часовом поясе проекта. В день дедлайна задача не просрочена.

Миграция: `task_pages/migrations/0001_initial.py`.
Импорт: `task_pages/management/commands/import_legacy.py`.
Представления: `task_pages/views.py`; шаблоны: `task_pages/templates/task_pages/`.
Обычный Python-класс `models/task.py` относится к консольной версии.
SQL-файлы и `db/` сохранены как материалы ПР7; веб-представления их не вызывают.

## Страницы и управление данными

- `/tasks/`: фильтры категории, статуса, предельной даты; поиск по названию
  или по названию и категории; сортировки по сроку, названию, категории.
- Пагинация по 10 задач. Ссылки сохраняют параметры; отправка формы сбрасывает
  страницу. Счётчик показывает весь отфильтрованный набор.
- Неизвестная сортировка заменяется стандартной; неверная дата даёт сообщение
  и пустой результат. Нечисловая страница открывает первую, выход за пределы — последнюю.
- `/tasks/<id>/`: карточка и до трёх других задач категории; отсутствующий ID даёт 404.
- `/tasks/active/`: невыполненные задачи; `/tasks/due/?date=2026-12-31`:
  невыполненные задачи со сроком не позже даты.
- `/tasks/statistics/`: общее число, выполненные, просроченные, ближайший срок,
  показатели по всем категориям, категории с несколькими задачами и без задач.
- `/admin/`: создание, редактирование и удаление задач и категорий через ORM.
  Для входа создать учётную запись: `python manage.py createsuperuser`.

SQLite `icontains` без дополнительных расширений не гарантирует поиск без учёта
регистра для кириллицы. Для русских слов следует сохранять регистр исходных данных.

## ORM-запросы для защиты

Ниже перечислены отдельные запросы/варианты запросов, реально используемые
в представлениях. Один составной запрос считается одной строкой.

| № | Назначение | Реализация |
|---|---|---|
| 1 | Список задач со связанными категориями | `Task.objects.select_related("category")` |
| 2 | Список категорий, сортировка по одному полю | `Category.objects.order_by("name")` |
| 3 | Фильтр по связанной модели | `filter(category__name=category)` |
| 4 | Исключение выполненных | `exclude(is_completed=True)` |
| 5 | Только выполненные | `filter(is_completed=True)` |
| 6 | Просроченные, два условия | `filter(is_completed=False, deadline__lt=...)` |
| 7 | Поиск по названию | `filter(name__icontains=query)` |
| 8 | Поиск по двум полям | `filter(Q(name__icontains=...) \| Q(category__name__icontains=...))` |
| 9 | Ограничение по сроку | `filter(deadline__lte=parsed_date)` |
| 10 | Сортировка по нескольким полям и пагинация | `Paginator(tasks_list.order_by(*SORTS[sort]), 10)` |
| 11 | Одна задача с категорией | `select_related("category").get(pk=task_id)` |
| 12 | Обратная связь и ограничение выборки | `task.category.tasks.exclude(pk=...).select_related("category")[:3]` |
| 13 | Невыполненные задачи к дате | `filter(is_completed=False, deadline__lte=...).order_by(...)` |
| 14 | Сводные показатели | `Task.objects.aggregate(...)` с `Count` и `Q` |
| 15 | Ближайший срок активной задачи | `filter(is_completed=False).aggregate(Min(...))` |
| 16 | Число задач в каждой категории | `Category.objects.annotate(...)` |
| 17 | Категории с несколькими задачами | `by_category.filter(tasks_count__gt=1)` |
| 18 | Только названия пустых категорий | `filter(tasks__isnull=True).values_list("name", flat=True)` |

Создание, чтение, изменение и удаление можно продемонстрировать в Django shell:

```python
from datetime import date
from task_pages.models import Category, Task

category = Category.objects.create(name="Демонстрация ПР9")
task = Task.objects.create(name="Проверить ORM", category=category,
                           deadline=date(2030, 1, 1))
task = Task.objects.get(pk=task.pk)
task.is_completed = True
task.save(update_fields=["is_completed"])
print(list(category.tasks.values("id", "name", "is_completed")))
task.delete()
category.delete()
```

## Назначение

**Трекер домашних задач** — приложение, которое помогает пользователю вести список домашних дел: добавлять задачи с указанием категории и дедлайна, отслеживать их статус и не пропускать сроки.

Консольная версия позволяет управлять задачами через меню в терминале. Веб-версия на Django отображает задачи и их карточки в браузере.

---

## Целевая аудитория

Пользователи, которым нужен простой инструмент для организации повседневных домашних дел без использования внешних сервисов и облачных платформ.

---

## Предметная область

Основной объект предметной области — **домашняя задача**. Задача описывается названием, категорией, дедлайном и статусом выполнения.

Пользователь может:
- добавлять задачи с названием, категорией и сроком выполнения;
- отмечать задачи выполненными и снимать отметку;
- искать задачи по подстроке названия;
- фильтровать задачи по категории;
- сортировать задачи по дедлайну;
- просматривать статус каждой задачи.

Статус задачи вычисляется автоматически:
- **«Задача выполнена»** — задача отмечена выполненной (`is_completed = true`);
- **«Задача просрочена»** — дедлайн прошёл, задача не выполнена;
- **«Задача в процессе»** — дедлайн ещё не наступил, задача не выполнена.

---

## Основные сущности

### Задача (Task)

Единственная сущность предметной области.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `int` | Уникальный числовой идентификатор, присваивается автоматически |
| `name` | `str` | Название задачи, например «Убрать кухню» |
| `category` | `str` | Категория задачи, например «Уборка», «Покупки», «Ремонт» |
| `deadline` | `str` (ISO 8601) | Дедлайн в формате `ГГГГ-ММ-ДД`, например `2026-10-15` |
| `is_completed` | `bool` | `true` — задача выполнена, `false` — ещё нет |

**Пример задачи:**

```json
{
  "id": 1,
  "name": "Убрать кухню",
  "category": "Уборка",
  "deadline": "2026-10-15",
  "is_completed": false
}
```

## Объектная модель

С ПР3 данные задач представлены не словарями, а объектами класса `Task` из модуля `models/task.py`.

### Класс `Task`

```python
from models import Task

task = Task(
    task_id=1,
    name="Убрать кухню",
    category="Уборка",
    deadline="2026-10-15",
)
```

**Атрибуты объекта:**

| Атрибут | Тип | Описание |
|---------|-----|----------|
| `task.id` | `int` | Идентификатор |
| `task.name` | `str` | Название |
| `task.category` | `str` | Категория |
| `task.deadline` | `str` | Дедлайн в формате ISO 8601 |
| `task.is_completed` | `bool` | Статус выполнения |

**Методы объекта:**

| Метод | Возвращает | Описание |
|-------|-----------|----------|
| `task.mark_completed()` | `None` | Отмечает задачу выполненной (`is_completed = True`) |
| `task.cancel_completion()` | `None` | Снимает отметку выполнения (`is_completed = False`) |
| `task.get_status()` | `str` | Возвращает текстовый статус задачи |
| `task.days_until_deadline()` | `int` | Количество дней до дедлайна (может быть отрицательным) |
| `task.is_overdue` | `bool` | Свойство: задача не выполнена, а дедлайн уже прошёл (используется в шаблонах) |
| `task.to_dict()` | `dict` | Преобразует объект в словарь для сохранения в JSON |
| `Task.from_dict(data)` | `Task` | Создаёт объект `Task` из словаря (classmethod) |
| `str(task)` | `str` | Строковое представление вида `[1] Убрать кухню (Уборка) — до 2026-10-15 — Задача в процессе` |

**Пример работы:**

```python
task = Task(1, "Убрать кухню", "Уборка", "2026-10-15")

print(task.get_status())        # Задача в процессе
print(task.days_until_deadline()) # количество дней

task.mark_completed()
print(task.get_status())        # Задача выполнена
print(task.is_completed)        # True

task.cancel_completion()
print(task.is_completed)        # False
```

**Сериализация и десериализация:**

```python
# Объект → словарь → JSON
data = task.to_dict()

# JSON → словарь → объект
task = Task.from_dict(data)
```

Данные хранятся в `data/tasks.json`. При загрузке каждый словарь преобразуется в объект `Task` через `Task.from_dict()`. При сохранении объекты преобразуются обратно через `task.to_dict()`.

| `main()` | `main.py` | Основной цикл консольного меню |

### Консольное меню

```
=== Трекер домашних задач ===
1. Показать все задачи
2. Найти задачу по названию
3. Фильтр по категории
4. Показать задачи по дедлайну
5. Добавить задачу
6. Отметить задачу выполненной
7. Снять отметку выполнения
0. Выход
```

## Веб-интерфейс

Веб-версия реализована на Django 5.2. С ПР6 HTML-страницы формируются шаблонами Django (Django Template Language): view-функция получает данные из базы данных SQLite, передаёт их в шаблон через контекст, а шаблон формирует HTML. Генерация HTML в Python-коде (функция `page()`) больше не используется.

С ПР7 данные для страниц выбираются SQL-запросами из SQLite (`data/tracker.sqlite`) средствами стандартного модуля `sqlite3`; JSON-файл остаётся исходными данными для переноса в базу. Django ORM, модели Django и формы пока не используются.

```
HTTP-запрос → URLconf → view → контекст → шаблон → HTML → HTTP-ответ
```

### Страницы

| URL | Имя маршрута | View-функция | Шаблон |
|-----|--------------|-------------|--------|
| `/` | `homepage:index` | `homepage.views.index` | `homepage/index.html` |
| `/tasks/` | `tasks:list` | `task_pages.views.tasks` | `task_pages/task_list.html` |
| `/tasks/<int:task_id>/` | `tasks:detail` | `task_pages.views.task_detail` | `task_pages/task_detail.html` |
| `/tasks/?category=Уборка` | `tasks:list` | `task_pages.views.tasks` | `task_pages/task_list.html` |
| `/tasks/active/` | `tasks:active` | `task_pages.views.active_tasks` | `task_pages/active_tasks.html` |
| `/tasks/due/?date=2026-11-01` | `tasks:due` | `task_pages.views.tasks_due` | `task_pages/tasks_due.html` |
| `/tasks/statistics/` | `tasks:statistics` | `task_pages.views.statistics` | `task_pages/statistics.html` |

Если задача с указанным `task_id` не найдена, шаблон показывает сообщение «Задача не найдена», а HTTP-ответ имеет статус **404**.

### Базовый шаблон и наследование

Общая HTML-структура страниц находится в `templates/base.html`: объявление документа, подключение Bootstrap и собственного CSS, логотип, навигация, подвал и подключение JavaScript. Базовый шаблон определяет два блока, которые переопределяют дочерние страницы:

```django
{% block title %}...{% endblock %}
{% block content %}...{% endblock %}
```

Дочерние шаблоны (`index.html`, `task_list.html`, `task_detail.html`) начинаются с `{% extends "base.html" %}` и содержат только содержимое страницы.

### Включаемые шаблоны

Повторяющиеся фрагменты вынесены в отдельные шаблоны и подключаются через `{% include %}`:

| Шаблон | Где подключается |
|--------|------------------|
| `includes/navigation.html` | `base.html` |
| `task_pages/includes/task_card.html` | `task_list.html` (в цикле по задачам) |
| `task_pages/includes/task_status.html` | `task_card.html` и `task_detail.html` |

### Контекст, циклы и условия

View передаёт данные словарём контекста:

```python
context = {"tasks": tasks_list}
return render(request, "task_pages/task_list.html", context)
```

В шаблоне используются `{% for task in tasks %}` с веткой `{% empty %}` для пустого списка и `{% if %}` для разных состояний данных: статус задачи (`task.is_completed`, `task.is_overdue`) и отсутствие задачи на странице 404.

### Цветовые бейджи статусов

Бейдж формируется в `task_status.html`; условие опирается на поля `is_completed` и `is_overdue`. Для объекта `Task` это атрибут и свойство, для строки результата SQL-запроса — столбцы (`is_overdue` вычисляется в запросе), поэтому один и тот же шаблон работает с обоими источниками данных.

| Статус | Цвет Bootstrap |
|--------|---------------|
| Задача выполнена | `bg-success` (зелёный) |
| Задача просрочена | `bg-danger` (красный) |
| Задача в процессе | `bg-warning text-dark` (жёлтый) |

### Фильтры шаблонов

Используются стандартные фильтры Django для представления данных:

```django
Всего задач: {{ tasks|length }}
{{ task.name|default:"Без названия" }}
```

Фильтры не содержат бизнес-логики. Дедлайн хранится как строка `ГГГГ-ММ-ДД` и выводится без преобразования средствами шаблона.

### Именованные URL и пространства имён

В `urls.py` каждого приложения задан `app_name` и имена маршрутов. Ссылки в шаблонах формируются тегом `{% url %}`, жёстко заданные адреса не используются:

```django
{% url 'homepage:index' %}
{% url 'tasks:list' %}
{% url 'tasks:detail' task.id %}
```

### Статические файлы

Статические файлы проекта находятся в `homepage/static/homepage/`:

| Файл | Назначение | Где используется |
|------|-----------|------------------|
| `css/style.css` | Собственные стили (карточки, статусы, логотип, подвал) | `base.html`, `task_card.html`, `task_status.html` |
| `js/main.js` | Выводит текущий год в подвале | `base.html` |
| `img/logo.png` | Логотип | `base.html` |

Подключение: `{% load static %}` в начале `base.html` и `{% static 'homepage/css/style.css' %}`. Bootstrap сохранён, но не заменяет собственный CSS.

### Маршрутизация URL

```
tracker/urls.py
├── path('', include('homepage.urls'))       →  /
│       homepage/urls.py   (app_name = "homepage")
│       └── path('', views.index, name='index')
│
└── path('tasks/', include('task_pages.urls')) → /tasks/...
        task_pages/urls.py (app_name = "tasks")
        ├── path('', views.tasks, name='list')                    → /tasks/
        ├── path('<int:task_id>/', views.task_detail, name='detail') → /tasks/1/
        ├── path('active/', views.active_tasks, name='active')    → /tasks/active/
        ├── path('due/', views.tasks_due, name='due')             → /tasks/due/?date=...
        └── path('statistics/', views.statistics, name='statistics') → /tasks/statistics/
```

## Хранение данных

Данные хранятся в файле `data/tasks.json` в виде списка объектов JSON.

**Пример содержимого файла:**

```json
[
  {
    "id": 1,
    "name": "Убрать кухню",
    "category": "Уборка",
    "deadline": "2026-10-15",
    "is_completed": false
  },
  {
    "id": 2,
    "name": "Купить молоко",
    "category": "Покупки",
    "deadline": "2026-10-01",
    "is_completed": true
  },
  {
    "id": 3,
    "name": "Починить кран",
    "category": "Ремонт",
    "deadline": "2026-09-20",
    "is_completed": false
  }
]
```

**Принцип работы с данными:**

```
При загрузке:
  JSON-файл → list[dict] → list[Task]  (через Task.from_dict())

При сохранении:
  list[Task] → list[dict] → JSON-файл  (через task.to_dict())
```

Преобразование выполняется исключительно в модуле `storage.py`. Остальные модули работают только с объектами `Task`.

Если файл не найден или содержит повреждённые данные, `load_tasks()` возвращает пустой список — приложение запускается без ошибок.

JSON-хранилище используется консольной версией и как источник для переноса данных в базу SQLite (см. [База данных SQLite](#база-данных-sqlite)); веб-страницы с ПР7 читают данные из базы.

## База данных SQLite

С ПР7 задачи хранятся в реляционной базе SQLite — файл `data/tracker.sqlite`. JSON-файл `data/tasks.json` сохраняется как исходные данные: из него база заполняется скриптом импорта. Работа с базой выполняется напрямую через SQL и стандартный модуль `sqlite3`; Django ORM и модели Django пока не используются. Служебная база Django `db.sqlite3` — отдельный файл.

### Структура базы данных

Две сущности предметной области: категория и задача. Одна категория содержит много задач; каждая задача относится к одной категории.

**Таблица `categories`:**

| Поле | Тип | Назначение |
|------|-----|-----------|
| `id` | `INTEGER` | первичный ключ (`PRIMARY KEY`) |
| `name` | `TEXT NOT NULL UNIQUE` | название категории |

**Таблица `tasks`:**

| Поле | Тип | Назначение |
|------|-----|-----------|
| `id` | `INTEGER` | первичный ключ (`PRIMARY KEY`) |
| `name` | `TEXT NOT NULL` | название задачи |
| `category_id` | `INTEGER NOT NULL` | внешний ключ на `categories.id` (`FOREIGN KEY`) |
| `deadline` | `TEXT NOT NULL` | дедлайн, строка `ГГГГ-ММ-ДД` (допускает сравнение и сортировку в SQL) |
| `is_completed` | `INTEGER NOT NULL DEFAULT 0` | `0` — не выполнена, `1` — выполнена (`CHECK (is_completed IN (0, 1))`) |

```
categories                 tasks
──────────                 ─────
id PK  ◄────────────┐      id PK
name UNIQUE         └───── category_id FK
                           name
                           deadline
                           is_completed
```

В JSON категория хранится строкой в каждой задаче; при импорте уникальные названия переносятся в `categories`, а в `tasks.category_id` записывается ссылка на строку этой таблицы.

### Получение данных в представлениях

```python
from db.database import get_connection

conn = get_connection()          # row_factory = sqlite3.Row
rows = conn.execute(
    TASK_SELECT + " WHERE tasks.id = ?",   # значение — отдельным параметром
    [task_id],
).fetchall()
```

Значения, полученные от пользователя (`?category=...`, `?date=...`, `task_id`), передаются в запрос только параметрами `?`; подстановка в текст запроса через конкатенацию или f-строки не используется. Благодаря `sqlite3.Row` шаблон обращается к полям по именам: `{{ task.name }}`, `{{ task.category }}`.

## Описание модулей

### `models/task.py`

Содержит класс `Task` — основную единицу данных приложения. Инкапсулирует атрибуты задачи и методы работы с её состоянием. Конвертация между объектом и словарём JSON реализована через `to_dict()` и `from_dict()`.

### `tasks.py`

Функции работы с коллекцией задач `list[Task]`:
- `add_task()` — создаёт объект `Task` и добавляет в список; `id` вычисляется автоматически как `max(id) + 1`;
- `find_task()` — поиск по подстроке в поле `name` (регистронезависимый);
- `find_task_by_id()` — поиск по числовому `id`;
- `filter_tasks_by_category()` — генератор, отдаёт задачи одной категории;
- `sort_tasks()` — сортировка по полю `deadline` с помощью `lambda`;
- `check_task_deadline()` — проверяет, осталось ли не менее `N` дней до дедлайна.

### `completions.py`

Функции управления статусом выполнения:
- `complete_task()` — вызывает `task.mark_completed()`, возвращает `False` если задача уже выполнена;
- `cancel_completion()` — вызывает `task.cancel_completion()`;
- `is_task_completed()` — возвращает значение атрибута `task.is_completed`.

### `storage.py`

Загрузка и сохранение данных:
- `load_tasks()` — читает JSON-файл, преобразует каждый словарь в объект `Task`; при ошибке возвращает `[]`;
- `save_tasks()` — преобразует объекты `Task` в словари и записывает в JSON.

### `utils.py`

Вспомогательные функции ввода:
- `input_int()` — повторяет запрос, пока пользователь не введёт корректное целое число;
- `input_date()` — повторяет запрос, пока не будет введена корректная дата в формате ISO 8601.

### `main.py`

Точка запуска консольной версии. Загружает задачи, отображает меню, вызывает функции из `tasks.py`, `completions.py`, `storage.py`. Не содержит бизнес-логики.

## Назначение модулей Django

### `tracker/settings.py`

Настройки Django-проекта:
- `INSTALLED_APPS` — зарегистрированы `homepage` и `task_pages`;
- `TEMPLATES['DIRS'] = [BASE_DIR / 'templates']` — каталог шаблонов уровня проекта (`base.html`, `includes/`);
  `APP_DIRS = True` — поиск шаблонов в каталогах приложений;
- `LANGUAGE_CODE = 'ru-RU'` — русская локализация;
- `TIME_ZONE = 'Europe/Moscow'` — московский часовой пояс;
- `DATABASES` — SQLite для служебных нужд Django.

### `tracker/urls.py`

Корневая маршрутизация: подключает URL-конфигурации приложений `homepage` и `task_pages`.

### `homepage/views.py`

- `index(request)` — вызывает `render(request, "homepage/index.html")`. Контекст не нужен: страница не выводит динамических данных.

### `task_pages/views.py`

С ПР7 view-функции выбирают данные SQL-запросами из SQLite (`db.database.get_connection()`, значения — параметрами `?`) и передают строки результата в шаблоны через контекст:

- `tasks(request)` — список задач с названием категории (`JOIN`); необязательный параметр `?category=` фильтрует по категории;
- `task_detail(request, task_id)` — одна задача по `id`; если строка не найдена, в контекст попадает `None`, шаблон показывает сообщение, а ответ получает статус **404**;
- `active_tasks(request)` — невыполненные задачи (`WHERE`);
- `tasks_due(request)` — невыполненные задачи со сроком не позже даты из `?date=`; некорректная дата отклоняется до обращения к базе;
- `statistics(request)` — сводка (`COUNT`, `SUM`, `MIN`), задачи по категориям (`LEFT JOIN`, `GROUP BY`) и категории с несколькими задачами (`HAVING`).

HTML в `views.py` больше не формируется.

## Текущее состояние и план развития

### Реализовано

- консольный интерфейс с полным набором операций над задачами;
- объектная модель (`Task`) с инкапсуляцией данных и методов;
- JSON-хранилище с сериализацией/десериализацией объектов;
- веб-интерфейс на Django: главная страница, список задач, карточка задачи;
- Django Template Language: базовый шаблон `base.html`, наследование,
  блоки, включаемые шаблоны, контекст, циклы и условия (ПР6);
- именованные URL и пространства имён (`homepage`, `tasks`);
- фильтры шаблонов (`length`, `default`);
- собственные статические файлы: CSS, JavaScript, логотип;
- функция `page()` и генерация HTML в Python удалены;
- база данных SQLite: две таблицы (`categories`, `tasks`), первичные и внешний ключи, схема `sql/schema.sql`, импорт данных из JSON (`db/import_json.py`) (ПР7);
- 16 SQL-запросов в `sql/queries.sql`: выборки, `WHERE`, `JOIN`, агрегатные функции, `GROUP BY`, `HAVING`, подзапрос;
- веб-страницы получают данные из SQLite через `sqlite3` и параметризованные запросы: список и карточка задач, фильтр по категории, активные задачи, поиск по сроку, статистика;
- навигация между разделами через именованные URL;
- автоматизированные тесты (45 штук, все проходят);
- соответствие кода стандарту PEP 8 (flake8).

### Ограничения текущего этапа

- Django ORM и модели Django не используются: база данных обслуживается напрямую через SQL и `sqlite3`;
- формы Django ещё не реализованы, данные через веб-интерфейс изменить нельзя;
- JSON-файл остаётся исходными данными и источником для импорта.

### Планируется

- переход от `sqlite3` и SQL к моделям Django и Django ORM;
- формы для создания, редактирования и удаления задач;
- фильтрация и поиск задач в веб-интерфейсе;
- авторизация пользователей;
- REST API (Django REST Framework);
- контейнеризация приложения (Docker);
- настройка CI/CD.
